# خطة اختبار رحلات المستخدمين

**Goal:** التحقق من أن كل مستخدم ينجز عمله ويحافظ على بياناته، ولا يتجاوز صلاحياته عبر الواجهة أو API.

**Architecture:** حساب مستقل وسياق متصفح مستقل لكل دور، ثم سيناريوهات كتابة واعتماد على قاعدة اختبار منفصلة. يُختبر الدور مع القسم والصلاحيات الفعلية والاستثناءات الشخصية، وليس المسمى الوظيفي فقط.

**Tech Stack:** Playwright، Vitest، React، TypeScript، Express، SQLite.

**Spec:** طلب المستخدم بتاريخ 2026-10-05، ومراجعة `docs/UI_UX_JOURNEY_REVIEW.md`.

## حدود التنفيذ والسلامة

- هذه خطة اختبار، وليست إقراراً بأن كل حالة أدناه نُفذت أو نجحت.
- الفحص المنفذ الآن: دخول الأدوار الأساسية العشرة والتنقل إلى ثلاث وجهات مرتبطة بكل دور، مع فحص منع الكتابة للمتدرب وإخفاء الإدارة للأدوار غير المخولة. المرجع `tests/e2e/role-journeys.spec.ts`.
- اختبار البث والحذف وتغيير الصلاحيات والاستعادة يُنفذ في بيئة اختبار فقط؛ لا يُستخدم الحساب المفتوح لدى المستخدم أو قاعدة `data` الحقيقية.
- الحسابات التجريبية تصلح فقط عند تشغيل البيانات التجريبية. لا تستخدم كلمة مرور مشتركة في الإنتاج.
- تُصدّر مصفوفة الصلاحيات الفعلية قبل الجولة: الدور، القسم، الدور المخصص، المنح والمنع الشخصيان، حالة الحساب. التعريف الافتراضي في `src/shared/rbac.ts` ليس بديلاً عن بيانات قاعدة النظام الجاري.
- يُستخدم مسار واحد متسلسل للبيانات المشتركة؛ لا تُشغّل سيناريوهات تغيّر نفس الخبر عشوائياً بالتوازي.
- النتيجة لكل حالة: لم يبدأ / ناجح / فاشل / محجوب، مع دليل وتاريخ ونسخة التطبيق. لا يُحسب المحجوب ناجحاً.

## رحلة وخطة كل نوع مستخدم

الأسماء التالية هي الأدوار الأساسية الموجودة في المصدر. مدير العمليات والإخراج والكنترول ليسوا ثلاثة أدوار مستقلة هنا؛ قد يكون المستخدم ADMIN أو CREW مع قسم أو صلاحية إضافية.

### 1. مدير النظام العام — SUPER_ADMIN

الحساب التجريبي: `admin@akhbar.tv`. الرحلة: الرئيسية ← المستخدمون والأدوار ← الإعدادات ← قاعدة البيانات ← سجل التدقيق.

| ID | السيناريو | النتيجة المطلوبة |
|---|---|---|
| SA-01 | إنشاء حساب ومنحه دوراً وقسماً ثم دخوله في سياق ثانٍ | صلاحياته تطابق التعيين لا صلاحيات المدير |
| SA-02 | تعطيل الحساب أثناء جلسته | الجلسة لا تستمر بتنفيذ أفعال محمية |
| SA-03 | إنشاء دور مخصص وتعديل منح/منع شخصي | أثر الصلاحيات يظهر بالواجهة والخادم؛ يُختبر تجاوز SUPER_ADMIN المعروف صراحة |
| SA-04 | نسخة احتياطية ثم استعادة في قاعدة اختبار | تطابق عدد السجلات والروابط؛ لا استعادة فوق النظام الحقيقي |
| SA-05 | فحص سجل أعمال الإدارة | الفاعل والوقت والكيان صحيحون ولا يقبل تزويرهم |

### 2. مدير قطاع الأخبار والبرامج — ADMIN

الحساب: `director@akhbar.tv`، القسم التجريبي `control`. الرحلة: الرئيسية ← النشرات/الحلقات ← المناوبات ← وضع الهواء ← التقارير.

| ID | السيناريو | النتيجة المطلوبة |
|---|---|---|

| AD-02 | اعتماد ونشر مادة عبر المراحل المسموحة | لا قفز غير قانوني بين الحالات؛ يسجل الفاعل |

اختبارات المتصفح تعمل على قاعدة تجريبية منفصلة بعد البناء. `tests/e2e/server.mjs` يعيد تهيئة `tests/e2e/.data`؛ لا توجّه الاختبارات إلى بيانات التشغيل. على Windows يمكن تشغيل الخادم منفصلاً وتحديد `E2E_EXTERNAL_SERVER=true` و`E2E_PORT=3995` لتجنب مشاكل إنهاء الخادم الآلي.

## Review Focus ومعايير القبول

- تعارض تعديل خبر واحد من شخصين: قفل واضح ورفض إصدار قديم مع المحافظة على عمل المستخدم.
- انقطاع الشبكة بعد إرسال الحفظ وقبل تأكيده: لا إنشاء مكرر ولا إغلاق كاذب.
- نص عربي طويل وقائمة كبيرة: لا قص للنص أو الأفعال؛ كل النتائج قابلة للوصول.
- اختلاف الدور والقسم والمنع الشخصي: التنفيذ يطابق الخادم وليس اسم الدور.
- تاريخ أمس واليوم والتوقيت عبر منتصف الليل: لا اختيار مادة قديمة تلقائياً ولا تقارير بتاريخ مضلل.

قبول الإطلاق المقترح: نجاح كل P1 وحالات منع الصلاحيات؛ صفر فقد بيانات أو نشر/بث غير مخول؛ توثيق كل P2 المتبقي بمالك وموعد. الأداء هدف يُقاس لا ادعاء: ظهور التحديث في المتصفحات المشتركة خلال 3 ثوانٍ في الشبكة المحلية السليمة، وقياس مستقل عند استخدام fallback أو شبكة بطيئة.

نموذج نتيجة الحالة: `ID | الدور والقسم | نسخة التطبيق | البيانات | الخطوات | المتوقع | الفعلي | الحالة | دليل/trace | المسؤول | إعادة الاختبار`.
